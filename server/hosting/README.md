# Размещение «Гарант-Сервис Самара»

## Что передавать на сервер

- `public/` — готовый сайт; только эта папка должна быть доступна из Интернета.
- `gss-private/` — обработчик SMTP, зависимости и пример конфигурации. Папка располагается рядом с `public/`, за пределами корня сайта.
- `server-config/` — примеры конфигураций веб-сервера, не файлы сайта.
- `manifest.json` — дата сборки, информация о новостях и контрольные суммы публичных файлов.

Сайт не требует базы данных и постоянно работающего Node.js. Для формы нужны PHP 8.2+ с OpenSSL, Mbstring и Sessions, исходящий доступ к SMTP и параметры почтового ящика. **Отправка писем не включена до настройки SMTP.**

## Порядок запуска

1. Сохранить копию действующего сайта и его настроек. Сначала развернуть новую версию на тестовом адресе.
2. Разместить `public/` и `gss-private/` рядом, например `/var/www/gss/public/` и `/var/www/gss/gss-private/`. Загружать весь репозиторий в публичную папку не нужно.
3. Для Nginx адаптировать `server-config/nginx.conf.example`: пути к сайту, сертификату и сокету PHP-FPM. Проверить `nginx -t`, затем перезагрузить конфигурацию. Пример рассчитан на размещение в корне домена.
4. Для Apache 2.4 в `public/.htaccess` уже включены кеширование, сжатие и запрет просмотра каталогов. Нужны разрешения `AllowOverride FileInfo Options Indexes AuthConfig`, `mod_headers`, `mod_deflate` и настроенный PHP. HTTPS включить в настройках виртуального хоста или панели хостинга; за обратным прокси редирект настраивает администратор сервера.
5. Создать `gss-private/config.php` из примера. Указать SMTP, `secret`, точные HTTPS-адреса в `allowed_origins`. Инструкция находится в `gss-private/README.md`. Для тестового поддомена добавить его адрес в `allowed_origins`.
6. Разрешить пользователю PHP запись только в приватную папку `rate-limits`. Не выдавать права 777. Секретный `config.php` и SMTP-пароль хранить только на сервере.
7. После заполнения настроек установить `enabled => true`, проверить заявку и фактическое получение письма на `info@gss.ru`.
8. Проверить главную страницу, оба слайдера, окна, мобильное меню, телефон, карту, HTTPS, ответы 404, сжатие и заголовки кеширования. Затем переключить основной домен. Старые индексируемые адреса gss.ru сопоставить с новыми разделами и настроить отдельные 301-редиректы до переключения.

Если структура каталогов отличается, задайте PHP-FPM переменную `GSS_FORM_CONFIG` с абсолютным путём к приватному `config.php`. При обновлении сайта не перезаписывайте этот файл и каталог `rate-limits`. Не удаляйте старые файлы JS/CSS сразу после выпуска: посетитель с открытой старой вкладкой ещё может обращаться к ним.

## RSS V1 на действующем SpaceWeb

### Подготовка и сверка

1. Соберите пакет через `npm run build:hosting` и проверьте его командой `npm run check:hosting`. При необходимости подготовить более свежий встроенный резерв используйте `npm run prepare:hosting`. GitHub Pages и автономное превью используют встроенный снимок.
2. До выкладки сравните SHA-256 нового `_hosting/manifest.json` с файлами действующего сайта. Зафиксируйте список добавляемых и заменяемых путей. Для RSS нужны `index.html`, файлы из `assets/`, на которые ссылается новый HTML, новый `api/news.php`, а также `gss-private/news/cache.php` и `gss-private/news/update.php`. Загружайте из `assets/` только новые или изменённые файлы, сохраняя ранее опубликованные хешированные файлы. Автономный `preview.html` для RSS V1 обновлять не требуется.
3. Сравните действующий `.htaccess` с предлагаемой вставкой. Проверьте, что существующее правило, в том числе общий перехват `/api/*`, не направит `/api/news` в обработчик формы. Если есть риск для `/api/request` или неясно, как запрос проходит через фронтенд-прокси, остановите выкладку до выяснения маршрутизации.
4. Сохраните вне web root резервные копии текущего `.htaccess`, `index.html` и каждого существующего файла из согласованного списка замен. Сохраните список новых путей для отката. Не выгружайте поверх сайта весь пакет. Исключите из списка изменений `api/request.php`, файлы формы, `gss-private/config.php`, SMTP-зависимости, `rate-limits`, действующие права доступа и настройки DNS.

### PHP и cron

Разместите `gss-private/news/` рядом с `public_html/`. Для штатной работы PHP CLI должен иметь cURL и SimpleXML, доступ к RSS по HTTPS и право создавать кеш в каталоге новостей. Веб-PHP нужен доступ на чтение каталога и кеша. Владелец задачи cron должен совпадать с пользователем веб-PHP либо на новом каталоге новостей нужно отдельно согласовать доступ. Действующие права формы и SMTP менять не требуется.

В примере ниже замените `/home/l/login` на реальный родительский каталог `public_html`. Проверьте путь к бинарнику PHP 8.4 и выполните первое заполнение по SSH:

```sh
/usr/bin/php8.4 -v
/usr/bin/php8.4 /home/l/login/gss-private/news/update.php
ls -l /home/l/login/gss-private/news/news-cache.json
```

В планировщике SpaceWeb укажите расписание `0 * * * *` и команду из примера. При работе напрямую с crontab используйте всю строку:

```cron
0 * * * * /usr/bin/php8.4 /home/l/login/gss-private/news/update.php >> /home/l/login/gss-private/news/update.log 2>&1
```

PHP хранит время обновления и до десяти новостей в `gss-private/news/news-cache.json`. Если загрузка или проверка не удалась, предыдущий кеш остаётся, а причина записывается в `update.log`. Одновременные запуски используют `news-update.lock`. [Инструкция SpaceWeb по cron](https://help.sweb.ru/planirovshik-zadach-cron_59.html)

### Выкладка и проверка

1. Добавьте в существующий `public_html/.htaccess` только правило ниже, перед общим перехватом маршрутов, если он есть. Если `RewriteEngine On` уже задан, повторять его не нужно.

   ```apache
   RewriteEngine On
   RewriteRule ^api/news$ api/news.php [END]
   ```

2. Загрузите `api/news.php` и проверьте `curl -i https://gss.ru/api/news`. Ожидаются HTTP 200, JSON с `updatedAt` и массивом `news`. Если кеш ещё отсутствует или повреждён, API вернёт HTTP 503 с кодом `NEWS_UNAVAILABLE`.
3. Загрузите новые ресурсы из `assets/`, затем замените `index.html`. В браузере проверьте карточки, даты, ссылки и один запрос к API за открытие страницы. После очередного запуска cron проверьте, что `updatedAt` продвинулось и в `update.log` нет ошибок.
4. Отправьте тестовую заявку через действующую форму и проверьте получение письма в корпоративном ящике. Если форма перестала работать, восстановите из копии `.htaccess` и `index.html`, верните остальные заменённые файлы, уберите добавленные маршрутом RSS файлы и отключите его cron. Затем повторно проверьте форму.

## Что ещё нужно от сервера

Операционная система, веб-сервер (Nginx/Apache/IIS), корень сайта, версия PHP и его расширения, доступ к DNS/HTTPS, параметры SMTP и способ загрузки файлов. Эти параметры в пакет не зашиты. На GitHub Pages PHP-форма не выполняется.
