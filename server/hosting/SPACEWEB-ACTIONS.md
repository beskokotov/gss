# Подготовка выпуска gss.ru в GitHub Actions

## Проверка выпуска

1. Перед первым коммитом сверить `git status --short --branch`, `git rev-parse HEAD` и `git ls-remote origin refs/heads/main`. Включить в проверяемую версию актуальные исходники RSS V1 и исправление карусели. Workflow берёт исходники из коммита на GitHub.
2. Когда workflow появится в основной ветке репозитория `beskokotov/gss`, открыть **Actions → Deploy gss.ru → Run workflow** и выбрать `main`. Для первого выпуска оставить `baseline_manifest` пустым.
3. Проверить итог задания и скачать артефакт `gss-spaceweb-<SHA>-<номер попытки>`. В `site/` лежат `index.html` и разрешённые файлы `assets/`. Рядом лежит `release-manifest.json` с SHA коммита, списком файлов, размерами и SHA‑256. Манифест нужен для сверки и хранится вне публичного каталога.
4. Для сравнения передать компактный JSON предыдущего манифеста в поле `baseline_manifest`. Итог задания покажет добавленные, изменённые и оставшиеся только в предыдущем выпуске файлы. Выбирайте манифест фактически выложенного выпуска, если цель — подготовить список изменений для сайта. Пути из предыдущего манифеста сохраняются на сервере.

Для локальной проверки после `npm run build:hosting` и `npm run check:hosting`:

```text
node scripts/prepare-spaceweb-release.mjs <новый-каталог> [путь-к-предыдущему-release-manifest.json]
```

Локальный манифест помечает незакоммиченные изменения полем `workingTreeClean: false`. В GitHub Actions требуется чистая копия конкретного коммита.

## Подключение SSH на следующем этапе

- Подтвердить в панели SpaceWeb доступ по SSH и его срок. Реквизиты выпуска: `bdvgssru@77.222.40.35:22`, корень сайта `/home/b/bdvgssru/public_html`. Проверить вход отдельным ключом с ограниченными правами и доступность сервера с runner. Приватный ключ подключить только к заданию публикации через Secret `SPACEWEB_SSH_PRIVATE_KEY` в окружении `spaceweb-production`. Включить ручное подтверждение и ограничение на `main`.
- Получить полное значение публичного ED25519-ключа сервера из доверенного источника и сверить его отпечаток с `SHA256:fDATcu43/zhAoS18DoD79nQjgUy1/Qmfq07t5VrDAew`. В репозитории **Settings → Secrets and variables → Actions → Variables** задать `SPACEWEB_SSH_HOST_KEY` в формате `ssh-ed25519 BASE64`, без имени хоста и комментария. Текущий workflow может проверить ключ локально и создать временный `known_hosts`, но сетевое подключение не выполняет. Будущее задание публикации должно повторить проверку и использовать `StrictHostKeyChecking=yes` вместе с `UserKnownHostsFile` для проверенного файла.
- Перед подтверждением публикации сравнить список с целевым каталогом. Сохранить вне web root копии каждого заменяемого файла и его SHA‑256. Передавать только проверенные файлы из `site/`, без `--delete`. Сначала установить ресурсы, затем атомарно заменить `index.html` переименованием в пределах одной файловой системы. Сохранить предыдущие хешированные ресурсы. `.htaccess`, `api/`, `gss-private/`, настройки SMTP и cron находятся вне публикации.
- После публикации проверить главную, JS/CSS, `/api/news` и форму. Для первой выкладки подтвердить получение тестовой заявки в корпоративном ящике. При регрессии восстановить заменённые ресурсы из копии, затем атомарно вернуть прежний `index.html` и повторить проверки.
